# Ordered FP64 Fortran contraction

`moment_kernel_real.f90` implements the existing real Cartesian s+p contraction
as a new backend. It changes neither quadrature nodes nor six angular moments,
radial payloads, channel selection, charges, electron translation factors, nor
the weak-form S/H/D definitions. It does not issue a physical operator query.

## C ABI

```c
int bass_moment_accumulate_real_f90_v1(
    size_t n, size_t nt, size_t np,
    const double *geo, const double *radt, const double *radp,
    const double *qt, const double *qp, const double *vel,
    const double *weights, const double *phase,
    double R, double Zt, double Zp, double *output);
```

The layout is identical to the reference C++ `bass_moment_accumulate_real_v1`:

| Argument | C row-major logical shape | Scalar representation |
| --- | --- | --- |
| geo | `(n,4)` = `r0,r1,axial,rho` | FP64 |
| radt / radp | `(n,nt,2)` / `(n,np,2)` | FP64 |
| qt / qp | `(nt,4)` / `(np,4)` | complex FP64, real/imag interleaved |
| vel | `(6,)`, target then projectile | FP64 |
| weights | `(n,6)` | complex FP64, real/imag interleaved |
| phase | `(n,)` | complex FP64, real/imag interleaved |
| output | `(4,nt,np)` = S, H, D_tp, conjugate D_pt | complex FP64, real/imag interleaved |

Fortran accesses flattened arrays explicitly; callers must not transpose them.
Inputs and output must not alias. The result **adds to existing output values**.
The final output block has the reference C++ orientation; the Python caller
performs the existing conjugate transpose of the fourth block.

Return codes: 0 succeeds; 1 rejects null pointers or dimensions outside
`1<=n<=4096`, `1<=nt,np<=128`; 2 rejects any nonzero imaginary part in qt or qp.
Shapes, allocation lengths, finite values, positive radii/R/charges, and output
finiteness remain checked by the Python boundary. The complex-coefficient path
uses the unchanged C++ general backend.

## Parallel and rounding contract

Matrix pairs `(i,j)` are flattened in C row-major order and grouped into tiles
of eight lanes. OpenMP statically partitions those tiles. Each lane has exclusive
ownership of one output element in every operator block. For every element, u
is traversed in the original increasing order; each addition to its accumulator
occurs in that order. There is no OpenMP/MPI floating reduction, no atomic add,
and no common mutable state. The serial remainder tile handles all shapes.

SIMD applies only to independent pair lanes. Explicit real/imaginary arithmetic
models the reference C++ `C` operations, including parenthesized left-associated
products and sums. Static and moving target derivative expressions are retained.
Their uniform branch occurs outside the SIMD lane loop.
Zero target velocity alone selects the original static-target branch.

Compile with, at minimum:

```sh
gfortran -O3 -fPIC -shared -fopenmp -fprotect-parens \
  -ffp-contract=off -fno-fast-math moment_kernel_real.f90 -o libmoments_f90.so
```

Do not add fast-math, reassociation, reciprocal approximations, or FMA contraction.
CPU-specific ISA flags may be used only when the resulting build receipt records
the host feature contract. This implementation's preserved evaluation order is
not a universal cross-compiler bitwise guarantee. Cross-backend numerical parity
and thread-count independence must be checked on each admitted toolchain. Preserve
batch boundaries (the current default is 1024); changing them changes the outer
Python summation grouping even when this kernel's u order is unchanged.

## Reproducible scalar expansion

The marked arithmetic and temporary declarations are generated by
`generate_lane_arithmetic.py`. The generator represents each complex operation
as the reference real/imaginary pair of scalar operations, then names its result.
It performs no algebraic simplification or reassociation. This removes GNU
Fortran's SIMD-private derived-type scatter stores, which prevented actual hot
loop vectorization in the initial implementation. Both static and moving hot
loops were subsequently reported as vectorized by GNU Fortran 13.3 with the
portable strict flags above; the integrated build retains its own vector report.

```sh
python generate_lane_arithmetic.py --check
```

Without `--check`, the generator refreshes only its marked regions in the Fortran
source. Compile the committed Fortran file directly; the generator is not a
runtime dependency. After expression changes, regenerate and rerun independent
C++ parity and thread-invariance checks. Preserve the first failing evidence.

## Work removed from the innermost loop

- Angular coefficient loads and target/projectile velocity dot products are
  computed once per channel per call.
- The angular coefficient dot product is computed once per `(i,j)` per call.
- `a-R`, the radial scalar product, and the Coulomb potential are computed once
  per quadrature node per call.
- The eight pair accumulators stay local to their tile until all n nodes finish.
- Six complex moments, phase, and geometric velocity products are shared by the
  pair lanes within one node/tile.

Scratch arrays scale as O(n + nt*np), in addition to caller-owned radial inputs;
there is no O(n*nt*np) materialized contribution tensor. All scratch lifetime is
one call, so cached values cannot survive a changed basis, geometry or velocity.

## MPI placement and integration seam

Use MPI to distribute independent identity-bound time/operator queries or complete
synthetic benchmark cases. Preserve the existing per-query ordered resolution
ladder and budget reservation. Do not parallelize a sequential propagator by
inventing an independent-time approximation. Do not partition this tiny 9x9 pair
matrix across 64 MPI ranks.

The number of MPI ranks times OpenMP threads must not exceed admitted CPUs.
Keep NumPy/BLAS libraries at one thread within each rank. Tune rank/thread layouts
on the target machine with its actual NUMA topology and measured rank RSS; 64 CPUs
and 128 GiB describe a target capacity, not a measured speedup or memory budget.
Synthetic local parity/throughput checks do not authorize new B0/native physics.

## Deferred optimizations

`exact_cross._radials` currently memoizes radial u,du but recomputes identical
`a,b` transforms across magnetic channels. A later cache may compute those
transforms once per complete radial payload and coordinate identity. Cache keys
must bind coefficient bytes, mesh edges, ell, evaluation coordinates and backend
identity. The same-center angular Y/gradient tensors can also be cached by the
full channel/angular-rule identity. Do not assume t and -t give interchangeable
phase or derivative data.

Replacing power sums by Horner evaluation, changing the quadrature batch size,
using tree/compensated reductions, or caching same-center matrices across changed
radial partitions would alter floating evaluation semantics and requires a
separate accuracy study. None of those changes is made here.
